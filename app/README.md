# Atlas, the app

Start here. The brief is in the [README](../README.md). The boards are the spec. They stay on the owner's Mac, out of the public repo: `canvas/project/` holds each board's HTML, CSS and SVG, which are the material the screens are built from; `cache/pictures/img/` has every screen as a picture; and the Studio has their stars and the owner's requests (see `WORKING.md`, also local). Atlas's own map engine, in Python, is `render/` (its README says how it draws from real data), and the data it draws from is `data/`.

Everything about the app is decided here, in its code and in this file. Nothing sits in between: no plan page, no procedure. A decision is written down the day it is made, under Decisions.

The code is `android/`: a Kotlin and Jetpack Compose project that builds from the command line and on GitHub (its README says how, which versions it stands on, and what each module is).

## The order

1. **The engine, 1:1.** `render/` ported to Kotlin and proven against the Python, drawn on the phone exactly as the renders look, from Atlas's own region packs (decisions 2 and 4).
2. **The app.** The screens, built from the boards' own elements: their SVG, CSS and symbols, not redrawn by eye.
3. **Traditions, further.** The plan's next places.

## Decisions

1. **Our own vector renderer, a port of `render/`.** The engine's look is drawn by our own code on the phone, not by an open-source renderer carrying its style.
2. **The engine is ported 1:1, and draws with Skia** (14 October; replaces 13 October's mesh renderer). The owner: everything 1:1 with the renders, at every zoom, from the same map data. The new `android/render` module ports `render/*.py` line by line, one Kotlin file per Python module: the same functions, constants, order and arithmetic, Python's random generator reproduced bit-exactly, and the same SVG text out. Differential tests prove it: the Python engine renders the same extract at the same camera, and the two SVGs are compared element by element. Zoom levels are camera distances in that same code, so the port carries them all. On the phone the SVG is parsed once per frame into a display list and drawn on Android's Canvas: Skia, as the browsers that drew the renders, so gradients, patterns, blend modes and text come out the same. The SVG filters (turbulence, displacement, colour matrices) are AGSL shaders on Android 13 and later. While a gesture runs, the last exact frame is warped to the new camera and the next exact frame is rendered behind it. Not OpenGL then; a real phone showed the frame rate needs it, and decision 9 takes it. Since 16 October the port draws the map: `mapview` renders exact frames from the region packs on a background thread and warps the last one under a gesture; the first, OpenMapTiles-based `engine` module is deleted.
3. **Modules** (13 October). `core` (geometry, the shared model), `tiles`, `render` (the engine, ported), `places`, `providers`, `search`, `route`, `guide` and `brouter` are plain Kotlin or Java, tested on the JVM against real data; `mapview` and `app` are Android. `android/README.md` has the map.
4. **The map data is our own** (14 October; replaces 13 October's OpenMapTiles). OpenMapTiles clips buildings at tile edges and drops the tags the engine draws from, so it cannot give 1:1. A region is an `.atlas` pack: the OSM elements with full tags and geometry, as the renders' Overpass extracts had them (lossless), the region's config (`data/regions/places.py`: origin, tradition, views), its elevation model, and an index to load what a view needs. The renders' own extracts are the first packs, published on GitHub as the release `packs-renders` (12 regions, 19 MB; the Westerkerk's pack is bundled in the app), so the app shows exactly the renders' data; elsewhere, packs are built from Geofabrik extracts on GitHub or from Overpass on the phone for a small area. No OpenFreeMap.
5. **The router is BRouter, embedded** (13 October). MIT, pure Java, vendored as source in `android/brouter` (commit 2989810, v1.7.10 + 13): no artifact exists on Maven Central. Its routing data for any place on Earth comes from brouter.de as 5° tiles (Amsterdam is `E0_N50.rd5`, 79 MB), updated daily with small diffs; we host nothing. Its data has no truck dimensions and no street names: Atlas checks a truck or boat route against OSM's limits and routes again around what does not fit, and names streets from its own map data. Valhalla routes trucks better but needs tiles someone builds and hosts; GraphHopper no longer runs on Android.
6. **The guide and the voice are our own** (13 October). Turn by turn, the eyes-free callouts, earcons and haptics are a pure Kotlin `guide`, tested on simulated drives; phrasing builds on osrm-text-instructions (BSD-2). The voice is Android's TextToSpeech with offline voices preferred. Not Ferrostar (a Rust core, less room for mode-specific callouts) and no neural voice inside the app: sherpa-onnx's TTS includes eSpeak NG (GPL-3), which Atlas's MIT licence cannot take; a neural voice comes as a separate TTS engine app.
7. **Providers** (13 October). Open and keyless by default: Overpass, Mangrove reviews, Open-Meteo, Wikidata, Photon/Nominatim, OSM notes, Open Food Facts prices. Keyed and optional, the key typed in by the user: Foursquare, Open Charge Map, Tankerkönig. **Chargemap has no public API**: using its data needs a partner agreement, so Atlas links out to it and keeps a key slot. Yelp is left out: its terms forbid showing it beside other reviews.
8. **GitHub builds, tests and releases** (13 October). Every push builds and tests on GitHub Actions and opens the APK on an Android emulator for screenshots (`.github/workflows/android.yml`); a `v*` tag publishes a signed release (`release.yml`). Offline packs are built there too and published as release assets (`packs.yml`). Alpha tags (`v0.1.0-alpha.1`) publish a debug build to test on a phone. The repository is public and holds the product only: the boards, the Studio and the session tools stay on the owner's Mac (14 October).
9. **The map is drawn on the GPU, visually 1:1** (16 October; replaces the Skia frames of decision 2 as what the screen shows). On the phone, the exact CPU frames took seconds to minutes, came out blurred at 2× and heated the phone without a picture: the owner found it "not usable as a maps app" and chose an OpenGL renderer of our own that reproduces the renders' look at the phone's resolution and 60 fps. The Python engine and its byte-identical port stay the truth: CI compares the GPU's pictures with their exact raster (about one colour level or less), and the engine runs in the background to make what the GPU draws, never per frame. The plan is being written; the first stage puts a fluid GPU map of the bundled Westerkerk on the phone.
